# Rin - Engineering Guidelines

## Verify

- `scripts/verify_code.sh`: fmt, clippy, tests and the image build (`--no-default-features --features hub,agent`),
  the release workflow's build checks (not its publish dry run). `scripts/verify_code.sh fast` is fmt + clippy;
  `scripts/verify_code.sh matrix` adds clippy on every feature subset.
- `scripts/verify_docker.sh`: needs Docker; starts a throwaway team and checks every service stays up (see below).
- `scripts/verify_docs.sh`: check the links between pages of the docs site inside `docs/`.
- `scripts/inspect_environment.sh`: checks this machine's development environment: git, hooks, the Rust
  toolchain (rustc ≥ 1.89, fmt, clippy), Docker and Compose (≥ 5.6). Run it when a check fails for reasons
  unrelated to the change, and before `scripts/verify_docker.sh` to see whether Docker is usable here.
- `scripts/pr_checks.sh [pr]`: waits for every status check on a pull request's head commit, then lists each
  check and the findings it annotated on the code. A passing check can still report findings.
- `scripts/sonar_issues.sh [pr]`: the SonarCloud check's open issues on a pull request, with rule keys, from the
  public API (no token). Its quality gate passes with open issues.
- One test: `cargo test --all-features <name>`. Plain `cargo test` skips the
  end-to-end tests in `src/tests.rs`, which need all three features.
- Git hooks live in `.githooks/`; enable them once per clone with `git config core.hooksPath .githooks`.
  `pre-commit` runs `scripts/verify_code.sh matrix` on the staged files (it skips commits that only touch
  Markdown, `assets/` or `.claude/`); agents must not bypass it with `--no-verify`.
  A cold build takes about two minutes, so give `git commit` and `scripts/verify_code.sh` a 10 minute timeout.
- Nothing here runs Docker or Linux. Say so when a change touches
  `src/compose.rs`, `images/Dockerfile` or container-only paths, run `scripts/verify_docker.sh` where Docker
  is available: it starts a throwaway team and checks every service stays up. HEAD must be pushed (the images
  build `rin` from GitHub at it), and a cold run can pass 10 minutes, so run it in the background.
  Without Docker, say those paths are unverified rather than claiming them verified.

## Gotchas

- Images install `rin` from a git revision (`RIN_GIT_REV`, default the `v<version>` tag), not from this working tree.
- `rin-schema.json` is the `rin.yml` contract and is embedded in the binary. Tests use
  `examples/team/rin.yml` as a fixture, so example edits can break tests.

## Changes

- Keep changes focused on the requested task.
- Follow existing conventions before introducing new ones.
- Avoid unnecessary dependencies and abstractions.
- Preserve compatibility across Cargo feature configurations.
- Do not break existing public interfaces without justification.
- Preserve persistent user data during generation, cleanup, and lifecycle changes.
- Before calling a non-trivial change done, run the `review-loop` skill: verify, independent review, fix, repeat.
- Open or push to a pull request through the `pr` skill: conventions, then status checks after every push.

## Commits

- Write short, clear commit messages.
- Do not include `Generated by` in commit messages.
- Split unrelated changes into understandable commits.
- Manifest files may be modified but must not be committed by the agent.
- Notify the human about manifest changes requiring a commit.

## Harness feedback

The harness is AGENTS.md, `.claude/` (settings, hooks, agents, skills), `.githooks/` and `scripts/`.
When it gets in your way, end your reply with a **Harness** section, one line per issue:
what happened, the evidence (file:line, command, error), and the fix you suggest. Report when:

- an instruction was wrong, stale, ambiguous or contradicted the code or another instruction;
- a permission prompt or deny rule blocked a legitimate step, or a risky step went through without one;
- a script or hook failed, was slow or was noisy for reasons unrelated to the change;
- a bug got past the verifier or review, so a check is missing;
- you repeated a manual step that a script or skill should do.

Report harness issues; do not fix harness files unless asked explicitly. Skip the section when there is nothing to report.

## Others

- Do not include `Generated by` in any message (including commit message, pr description, pr commits and the other messages).
