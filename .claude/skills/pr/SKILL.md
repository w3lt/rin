# Pull request

Open a pull request to `main`, or push more work to an existing one, and leave it with
no open SonarCloud findings. Issue or PR from the user (a number is the issue to close, unless
the current branch already has a PR): $ARGUMENTS

Current state:

!`git status -sb`

!`git log --oneline origin/main..HEAD || true`

!`gh pr view --json number,url,state -q '"#\(.number) \(.state) \(.url)"' 2>/dev/null || echo "no PR for this branch yet"`

## 1. Before pushing

- `git fetch`. Work on a branch, never on `main`: `feature/#<issue>-<slug>` from `origin/main`
  when there is an issue, otherwise `feature/<slug>`. Releases use the `release` skill instead.
- Run the `review-loop` skill. It verifies, reviews and commits.

## 2. Push

- Someone else pushed to the branch: `git pull --rebase` first. Main moved on after you pushed:
  merge `origin/main` rather than rebase. Never rewrite pushed commits or force-push.
- No PR yet: `gh pr create --base main --title '<title>' --body-file <file>`, writing the body
  file outside the repo (the scratchpad or a `mktemp` file), with:
  - **Title:** the commit form `.githooks/commit-msg` enforces, `<type>[(scope)]: <summary>`.
  - **Body** (see #6 for the shape):
    - `Closes #<issue>.` when there is one;
    - one paragraph on what the PR does, then bullets on what changed and why;
    - `Manifests:` what changed in `Cargo.toml`/`Cargo.lock` for the user to commit, if anything;
    - `Verified with` the exact scripts run, and whether Docker ran. Without Docker, name the
      container paths the PR touches as unverified.
  - No "Generated by" text.

## 3. SonarCloud (after every push)

The repo has no CI on pull requests; SonarCloud is the only check, and its quality gate passes
even with open issues. A green check is not enough: read the findings.

1. Run `scripts/sonar_issues.sh` on the branch, or `scripts/sonar_issues.sh <pr>` from elsewhere
   (background it; it waits up to 10 minutes for the analysis of the PR's head commit). Exit 0: nothing open, stop. Exit 1: triage. Exit 2: report the error.
2. Triage each finding against the code:
   - Real: fix it in the style of the surrounding code.
   - False positive, or it would break a repo convention: do not change code. Note the rule,
     `file:line` and a one-line reason for the user; marking it in SonarCloud needs write access.
   - In code the PR did not touch: list it for the user instead of fixing it.
3. Commit the fixes (`fix(<scope>): address SonarCloud findings` or a more specific message),
   run `scripts/verify_code.sh` (or `fast` when only scripts changed), push, and repeat from 1.
   Stop after 3 rounds and tell the user what is still open.

## Report

End with: the PR URL; Sonar rounds and findings fixed; findings left for the user to mark, with
reasons; manifest changes to commit; Docker/Linux paths nobody ran; and harness issues per
AGENTS.md "Harness feedback", or "Harness: none".
